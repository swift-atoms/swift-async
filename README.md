# swift-async

Use this package when you are building a concurrency type yourself and need one of its small parts: a lock (`Async.Mutex<Value>`), a one-shot value that many waiters await (`Async.Promise<Value>`, `Async.Gate`), a cancellation source with handlers (`Async.Cancellation.Source`), a single-slot hand-off (`Async.Publication<Value>`), a backpressure count (`Async.Demand`), a guarded completion state machine (`Async.Completion<Success, Failure>`), a shutdown state (`Async.Lifecycle.State`), an outcome tie-break (`Async.Precedence`) or a deferred async computation (`Async.Callback<Value>`). To pass a stream of values between tasks, or for a ready-made semaphore, barrier or broadcast, use the swift-async-* packages in swift-molecules (for example swift-async-channel) instead.

## Laws

- `Async.Mutex<Value>` is not reentrant. Under Embedded Swift, or where none of Darwin, Synchronization or Kernel_Thread is available, it is a plain box with no locking: `withLockIfAvailable` always runs its body. Use it there only from one thread.
- `Async.Promise<Value>`: the first `fulfill` wins; later calls return `false` and leave the value unchanged. Every waiter receives the value. Waiters registered before fulfillment are resumed by the fulfilling caller, in registration order, after the lock is released, so `wait` callbacks run on that caller; a `wait` after fulfillment runs its callback at once on its own caller. `value()` ignores task cancellation: a cancelled awaiter keeps waiting and receives the value.
- `Async.Cancellation.Source.cancel()` returns `true` exactly once, also under concurrent callers. Handlers run exactly once, on the cancelling caller, in registration order, outside the lock, and may call back into the source. A handler registered after cancellation runs immediately on the registering caller, and its `deregister()` returns `false`; so does `deregister()` after the handler has run or a second `deregister()`. A deregistered handler never runs.
- `Async.Publication<Value>`: the latest `publish` overwrites any untaken value; `take()` empties the slot, so of concurrent `take()` calls exactly one receives the value.
- `Async.Demand` saturates instead of overflowing: finite counts clamp to `maximumFiniteCount`, so finite addition never reaches `.unlimited`; `.unlimited` absorbs addition, survives `subtracting` and `fulfill()`; subtracting `.unlimited` or more than is left gives `.none`; `fulfill()` on `.none` returns `false`. `.unlimited` orders above every count.
- `Async.Completion<Success, Failure>` allows only `start()` pending→running, `complete(_:)` and `timeout()` running→terminal, `cancel()` from pending or running, and `fail(_:)` from pending. Every other call throws and changes nothing. The terminal transition resumes the continuation set by `set(continuation:)` at most once; a continuation set after the terminal transition, or replaced by a later `set(continuation:)`, is never resumed.
- `Async.Lifecycle.State`: `shutdown.begin()` succeeds only from `open` and `shutdown.complete()` only from `closing`; otherwise they return `false` and leave the state unchanged, so `closing` cannot be skipped.
- `Async.Precedence.resolve`: shutdown beats cancelled beats timeout beats success, and only the chosen outcome is evaluated.
- `Async.Callback<Value>` runs nothing until called, runs again on every call (nothing is cached), and runs in the caller's isolation, through `map` and `flatMap` too. `flatMap` with `init(value:)` satisfies left and right identity. The function given to `init(wrapping:)` must call its completion exactly once: twice traps, never suspends the caller forever.
- `Async.Continuation<T>` built from a `CheckedContinuation` must be resumed exactly once; built from a callback, each `resume(returning:)` calls the callback again.
